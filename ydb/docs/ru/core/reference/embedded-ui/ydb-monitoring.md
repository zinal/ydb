# {{ ydb-short-name }} Monitoring

{{ ydb-short-name }} Monitoring представлен набором web-страниц, отображающих состояние системы в разрезе по нескольким аспектам. На страницах приведены перечни компонент и их мгновенные параметры. Для многих компоненты приведен [цветовой индикатор](#colored_indicator) состояния перед названием.

## Главная страница {#main_page}

Страница доступна по адресу:

```text
http://<ендпоинт>:8765/monitoring/cluster
```

или с указанием вкладки:

```text
http://<ендпоинт>:8765/monitoring/cluster/<вкладка>
```

Примерный внешний вид страницы показан на скриншоте ниже.

![Monitoring_main_page](_assets/monitoring_main_page.png)

В верхней части страницы расположена краткая сводка информации о кластере:

* **CPU** — суммарная загрузка пулов акторной системы на всех узлах;
* **Memory** — суммарное потребление оперативной памяти узлами кластера;
* **Storage** — занято/всего доступно места на дисках;
* **Network** — [использование сети](#network_usage);
* **Nodes** — количество узлов.

Далее следуют вкладки:

* **Databases** — [список баз данных](#tenant_list_page) (ранее Tenants);
* **Nodes** — [список узлов](#node_list_page);
* **Storage** — группы хранения и узлы хранения;
* **Network** — состояние сетевых соединений между узлами;
* **Versions** — перечень версий {{ ydb-short-name }} на узлах кластера;
* **Tablets** — таблетки кластера;
* **Events** — события;
* **Configs** — конфигурация.

Также доступен отчёт Healthcheck по состоянию кластера.

Устаревшие адреса `/monitoring/tenant` и `/monitoring/cluster/tenants` перенаправляют на `/monitoring/database` и `/monitoring/cluster/databases` соответственно.

### Список баз данных {#tenant_list_page}

{{ ydb-short-name }} — мультиарендная СУБД, позволяющая изолировано обрабатывать запросы к базам различных пользователей, называемых тенантами. Каждая база данных принадлежит одному тенанту. В интерфейсе список тенантов отображается как вкладка **Databases**.

В списке баз данных для каждой базы приведены:

* **Database** — путь базы данных;
* **Type** — тип базы данных;
* **State** — состояние;
* **CPU** — загрузка CPU узлами базы данных;
* **Memory** — потребление ОЗУ узлами базы данных;
* **Storage** — оценка объема данных, хранимых базой данных;
* **Network** — исходящий трафик Interconnect;
* **Nodes** / **Groups** — количество узлов и групп хранения;
* **Pools** — потребление CPU узлами в разбивке по внутренним пулам потоков.

Тенант типа `Domain` обслуживает системные компоненты, необходимые для обеспечения работы всех тенантов. В него входят все storage узлы и системные таблетки. Тенант типа `Dedicated` выполняет обслуживание базы данных.

При нажатии на путь базы данных можно перейти на [страницу базы данных](#tenant_page).

### Список узлов {#node_list_page}

В списке указаны все узлы кластера. Для каждого узла приведены:

* **#** / **Node ID** — ID узла;
* **Host** — хост на котором располагается узел;
* **Endpoints** — прослушиваемые порты;
* **Version** — выполняемая версия {{ ydb-short-name }};
* **Uptime** — время работы узла;
* **Memory used** — используемый объем ОЗУ;
* **Memory limit** — установленное через cgroup ограничение потребления OЗУ;
* **Pools usage** — потребление CPU в разбивке по внутренним пулам потоков;
* **Load average** — средняя загрузка хоста по CPU.

При нажатии на имя хоста, можно перейти на [страницу узла](#node_page).

## Страница узла {#node_page}

Страница доступна по адресу:

```text
http://<ендпоинт>:8765/monitoring/node/<node-id>/
```

Информация об узле представлена следующими блоками:

* **Pools** — потребление CPU в разбивке по внутренним пулам потоков, примерное предназначение пулов:

  * **System** — задачи критически важных системных компонентов;
  * **User** — пользовательские задачи, выполнение запросов таблетками;
  * **Batch** — длительные фоновые задачи;
  * **IO** — выполнение блокирующих операций ввода-вывода;
  * **IC** — обработка сетевого взаимодействия.

  Высокая загрузка пулов может быть причиной деградации производительности и увеличения времени отклика системы.

* **Common info** — базовая информация об узле:

  * **Version** — версия {{ ydb-short-name }};
  * **Uptime** — время работы узла;
  * **DC** — зона доступности в которой расположен узел;
  * **Rack** — идентификатор стойки в которой располагается узел.

* **Load average** — средняя загрузка CPU хоста за разные интервалы времени:

  * 1 минута;
  * 5 минут;
  * 15 минут.

На странице узла есть вкладки:

* **Storage** — [список групп хранения](#node_storage_page);
* **Structure** — структура компонентов узла;
* **Tablets** — [список таблеток](#node_tablets_page);
* **Threads** — потоки пулов и использование CPU;
* **Network** — сетевые соединения узла;
* **Configs** — конфигурация узла.

### Список групп хранения на узле {#node_storage_page}

Для storage узлов список содержит группы хранения, хранящие данные на диске на данном узле. Для dynamic узлов показаны группы хранения принадлежащие тенанту к которому относится узел.

Группы хранения сгруппированы по пулам хранения. Каждый пул можно развернуть в список групп.

Для каждой группа приведены:

* ID группы хранения;
* индикатор быстродействия группы;
* количество VDisk'ов в группе;
* топология хранения данных.

Каждую группу хранения также можно раскрыть в список VDisk'ов, где для каждого VDisk'а приведены:

* VDiskID;
* уникальный в пределах узла PDiskID, на котором находится VDisk;
* ID узла, на котором находится VDiks;
* свободное/доступное место на блочном устройстве;
* путь, используемый для доступа к блочному устройству.

Данный список можно использовать для идентификации групп хранения на которые оказали влияние выход из строя дисков или узлов.

### Список таблеток на узле {#node_tablets_page}

Многие компоненты {{ ydb-short-name }} выполнены в виде таблеток. Система может перемещать таблетки между узлами. На любом из узлов может выполняться некоторое количество таблеток.

В верхней части списка таблеток расположен крупный индикатор работы таблеток на данном узле. Он показывает долю полностью запущенных и работающих таблеток.

Ниже индикатора располагается список таблеток, где каждая таблетка представлена маленьким значком [цветового индикатора](#colored_indicator). При наведении на индикатор отображается краткая информация о таблетке:

* **Tablet** — ID таблетки;
* **NodeID** — ID узла, на котором работает таблетка;
* **State** — состояние таблетки;
* **Type** — тип таблетки;
* **Uptime** — время работы с момента текущего запуска таблетки;
* **Generation** — поколение (номер текущей попытки запуска) таблетки.

## Страница базы данных {#tenant_page} {#database_page}

Страница доступна по адресу:

```text
http://<ендпоинт>:8765/monitoring/database?database=<путь-базы>
```

В левой панели навигации доступны разделы:

* **Database** — обзор базы данных и основные вкладки;
* **Diagnostics** — подробная диагностика;
* **SQL Editor** — исполнение YQL-запросов, история и сохранённые запросы.

Параметры URL:

* `database` — путь базы данных (устаревший параметр `name` также поддерживается);
* `databasePage` — раздел: `database`, `diagnostics` или `query`;
* `diagnosticsTab` — активная вкладка внутри раздела;
* `metricsTab` — активная метрика на Overview: `cpu`, `storage`, `memory` или `network`.

Пример открытия метрики сети:

```text
http://<ендпоинт>:8765/monitoring/database?database=<путь-базы>&diagnosticsTab=database&metricsTab=network
```

### Overview и метрики ресурсов {#database_overview}

На вкладке **Overview** (`diagnosticsTab=database`) отображается сводка по ресурсам базы данных:

* **CPU** — суммарная загрузка пулов акторной системы базы данных, кроме пула **IO**;
* **Storage** — объём данных, хранимых в базе, включая пользовательские данные и индексы;
* **Memory** — суммарное потребление памяти процессами базы данных;
* **Network** — [использование сети](#network_usage).

Для каждой метрики доступны дополнительные графики и списки наиболее нагруженных объектов (узлы, шарды, таблицы, запросы — в зависимости от метрики).

### Network usage {#network_usage} {#tenant_network}

Карточка **Network usage** показывает две величины:

1. **Интенсивность трафика** (например, `X MB/s`) — суммарный исходящий трафик Interconnect базы данных.
2. **Процент** — средняя утилизация исходящих очередей Interconnect по узлам базы данных.

Как считаются значения:

* **Трафик.** На каждом узле учитываются байты, записанные в сокеты peer-сессий Interconnect. По дельтам этих счётчиков вычисляется исходящая скорость для соединений с другими узлами; скорости по peer-сессиям суммируются. Для базы данных значения узлов суммируются. В карточке отображается именно этот исходящий bandwidth; входящий трафик и клиентский gRPC в эту величину не входят.

* **Процент.** На каждом узле считается доля времени, в течение которого хотя бы одна сессия Interconnect имела данные в исходящей очереди. Это отношение времени «есть что отправлять» к общему времени наблюдения, а не отношение трафика к пропускной способности сетевого интерфейса или канала. Для базы данных берётся среднее значение по узлам, которые отдают метрику.

Отображение процента можно отключить в настройках UI опцией **Show network utilization**.

Подробная таблица соединений между узлами доступна на вкладке **Network** базы данных или кластера.

### Другие вкладки базы данных

На странице базы данных также имеются следующие вкладки:

* **Queries** / **Top shards** — наиболее ресурсоёмкие запросы и шарды;
* **Storage** — [список групп хранения](#tenant_storage_page), содержит информацию о том, какие VDisk'и на каких узлах и устройствах работают; доступны фильтры вроде `Groups` / `Nodes`, `Degraded`, `Out of Space`;
* **Nodes** — [список узлов](#tenant_compute_page), содержит узлы и таблетки, запущенные на них (ранее вкладка Compute);
* **Tablets** — таблетки базы данных;
* **Network** — состояние сетевых соединений;
* **Info**, **Describe**, **Access**, **Configs**, **Operations**, **Backups**, **Monitoring** — информационные и операционные вкладки.

Также доступен отчёт Healthcheck по состоянию базы данных.

Здесь отображен список узлов принадлежадих текущей базе данных. В случае если тенант имеет тип domain, то в список входят storage узлы.

Каждый узел представлен следующими параметрами:

* **#** — ID узла;
* **Host** — хост на котором располагается узел;
* **Uptime** — время работы узла;
* **Endpoints** — прослушиваемые порты;
* **Version** — выполняемая версия {{ ydb-short-name }};
* **Pools usage** — потребление CPU в разбивке по внутренним пулам потоков;

### Схема базы данных и SQL Editor {#tenant_scheme}

В левой части страницы показано дерево схемы объектов базы данных, позволяющее выбирать конкретные таблицы и просматривать информацию о них.

В правой части расположены вкладки:

* **Info** — информация о таблице и ее схема;
* **Preview** — превью первых элементов таблицы;
* **Graph** — различные встроенные графики c информацией о состоянии таблицы;
* **Describe** — результат выполнения соответствующей команды;
* **Tablets** — перечень таблеток обслуживающих таблицу;
* **ACL** — Access Control List, список конроля доступа;
* **Top queries** — топ запросов к таблице по времени выполнения;
* **Top shards** — топ загруженных шардов таблицы.

Выполнение YQL-запросов доступно в разделе **SQL Editor** (`databasePage=query`), а не во вкладке **Query** на схеме, как в предыдущих версиях UI.

## Мониторинг статической группы {#static-group}

Чтобы проверить статус статической группы, перейдите на вкладку **Storage** на странице кластера или базы данных. По умолчанию отображается список групп, имеющих какие-либо проблемы.

В поисковой строке введите `static`. Если результат пуст, то статическая группа не имеет проблем. Если же в выдаче присутствует группа **static**, то необходимо проверить статус VDisk'ов в ней. Допустимы зеленый (проблем нет) и синий (VDisk реплицируется) состояния. Красный индикатор сигнализирует о проблеме. Наведите курсор на индикатор чтобы получить текстовое описание проблемы.

## Индикаторы состояний {#colored_indicator}

Слева от названия конкретного компонента может находится цветовой индикатор его состояния.

Цвета индикаторов имеют следующее значение:

* **Зеленый** — проблем нет, компонент работает в штатном режиме;
* **Синий** — происходит репликация данных, других проблем нет;
* **Желтый** — возможны проблемы, компонент продолжает работать;
* **Красный** — имеются критические проблемы, компонент не работает или работает с ограничениями.

Если компонент включает в себя другие компоненты, то в случае отсутствия собственных проблем, его состояние определяется путем агрегирования состояний его частей.
